# Cross-implementation interop

This directory runs Dialog's two implementations against **each other**, in both
directions, over the transport profile of
[`spec/07-transport.md`](../spec/07-transport.md).

```
        Go server  ←  TypeScript client        TypeScript server  ←  Go client
             \                                          /
              \______  the same summary document  ______/
```

Each implementation's suite already proves that it agrees with the
specification, with `vectors/` and with itself. Neither proves the thing an
interoperability profile exists for: that two programs written from the same
prose, by agents that never read each other's source, put the same blocks in the
same store when they talk over a socket. That is what this proves, and it is why
the harness asserts on a document neither implementation defines.

## Running it

```bash
./interop/run.sh
```

It needs Go and Node, which the repository invokes through nix:

```bash
nix shell nixpkgs#go nixpkgs#nodejs_24 --command ./interop/run.sh
```

The script builds `go/cmd/dialog-serve` and `go/cmd/dialog-sync`, installs `ts/`'s
dependencies if they are missing, starts servers on loopback ports the kernel
picks, runs every combination, and writes what it found to stdout. It leaves
nothing behind: every server is killed on exit, and the summaries go to a
temporary directory (`-keep DIR` puts them somewhere you can read them).

CI runs the same script on every push and pull request
([`.github/workflows/interop.yml`](../.github/workflows/interop.yml)).

## What is run

Three scenarios, each of them a *set of servers* and *one client*:

| Scenario  | Servers                                          | What it exercises |
|-----------|--------------------------------------------------|-------------------|
| `demo`    | one, over [`demo/chains/`](../demo/chains)        | three honest chains, 14 blocks, cross-chain `refs`, the ordinary case |
| `fork`    | two, over `fixtures/fork-a` and `fixtures/fork-b` | one author, a shared prefix, a divergent block on each side — validation rule 9 |
| `genesis` | two, over `fixtures/genesis-a` and `-b`           | one author, two chains with **no block in common** — rule 9 at the genesis position |

Each scenario is run under every **server layout** — which implementation is
behind each of its directories — and every layout is synced by **both** clients:

| Layout  | Servers                                                  |
|---------|----------------------------------------------------------|
| `go`    | all Go                                                   |
| `ts`    | all TypeScript                                           |
| `mixed` | the first Go, the second TypeScript (two-server scenarios only) |

So `go` servers × the TypeScript client and `ts` servers × the Go client are the
two crossings this directory exists for; `go`×Go and `ts`×TypeScript come along
for one process each and are what tells a real interop failure apart from a plain
bug — a scenario that fails everywhere is one implementation's bug, and one that
fails only across the diagonal is a disagreement about the profile. The `mixed`
layout is the case where a single client is reading one chain from two
implementations at once, which is the shape a fork is actually found in.

## What is asserted

Every run produces one **summary document**, and the harness makes two kinds of
assertion about it:

1. **Against the expectation.** `expected/demo.json`, `expected/fork.json` and
   `expected/genesis.json` say what a conforming client MUST end up holding.
   They are generated by `go/cmd/geninterop` **analytically** — from the fixture
   blocks, not by recording a client — so they are something both
   implementations are measured against rather than something one of them
   defines. Every digest in them is a fact about the committed bytes.
2. **Against each other.** The document produced by the Go client and the
   document produced by the TypeScript client, over the same servers, must be
   **identical** — and so must the two crossings, the TypeScript client's answer
   from Go servers and the Go client's answer from TypeScript servers, which are
   the two directions of one exchange. This is the assertion the directory exists
   for, and it is why
   the document contains no request counts, no source URLs, no timings and no
   implementation name: two conforming clients differ in all of those and in
   nothing that matters.

Every scenario is run **twice** against the same servers, differing only in where
a client asks a source it has not used before from — `-from genesis`, and
`-from held`, the position the client's own chain already reaches. The profile
permits both and says which is neither (`todos/099`), and they are not the same
exchange: from the genesis position the source re-sends the shared prefix and the
divergence arrives in the range; from the held position the source answers an
empty range and a tip the client cannot reach, which is the case "Pursuing an
advertised tip" is written for. The blocks that end up in the store are the same
either way — that is asserted — and the second pass additionally asserts that the
backward walk happened and ended by the name that scenario's divergence requires:
`held` where the two chains share a prefix, `genesis` where they share nothing.
That is [`spec/07-transport.md`](../spec/07-transport.md)'s three-way outcome,
crossed between the implementations rather than tested twice in isolation.

And one more, before any client has asked anything:

3. **The servers against each other.** Two servers over the same directory must
   announce the same blocks and the same tips in their startup line. A tip is the
   end of a forward walk over the blocks a source holds, and which branch of a
   fork that walk follows is fixed by the profile's reference rule — the lowest
   digest — rather than left to the server, so two conforming servers over one
   directory have one answer between them.

Concretely, for `demo` that means 3 chains, 14 blocks, every block accepted,
nobody's tip in doubt and no forks anywhere; for `fork`, one fork at the shared
prefix's last block with both divergent blocks as its sibling set, and a chain
whose tip is the lower-digest branch — from both directions, with the same
digests; for `genesis`, one fork at the **genesis position** whose sibling set is
the two genesis blocks.

## The summary document

```json
{
  "chains": [
    {
      "author": "b5ua…",
      "advertised_tips": ["bafyrei…", null],
      "tip": "bafyrei…",
      "chain": ["bafyrei…", "…"],
      "blocks": ["bafyrei…", "…"],
      "accepted": 6,
      "held": 0,
      "rejected": 0,
      "pursuits": [{"source": 1, "tip": "bafyrei…", "end": "genesis", "fetched": 2}],
      "forks": [{"prev": "bafyrei…", "siblings": ["bafyrei…", "bafyrei…"]}]
    }
  ],
  "totals": {"chains": 3, "blocks": 14, "accepted": 14, "held": 0, "rejected": 0, "forks": 0}
}
```

Every field is a fact about the blocks or about the client's own store. All keys
are always present, and every list is present rather than null, so that a reader
never has to tell absent from empty.

- **`author`** — the key in the canonical text form of
  [`spec/03-encoding.md`](../spec/03-encoding.md). Chains appear in the order
  they were asked for, which is also the order they were synced in.
- **`advertised_tips`** — what each source claimed, one entry per source in the
  order the sources were given on the command line, `null` where a source
  claimed no tip. It is a claim and not evidence: two sources differing means one
  is behind, or they are on different branches, or one is withholding, and the
  first and the third are indistinguishable.
- **`tip`** — the client's **own** tip after the sync, by the profile's
  constructive definition: the end of the forward walk from the genesis position
  through the blocks it holds, taking the lowest digest at a fork
  (`spec/07-transport.md`, "tip"). `null` where the walk reaches nothing.
- **`chain`** — that walk, genesis first.
- **`blocks`** — every block of the author the store holds that is reachable
  forward from the genesis position, **ascending by digest**: every branch of
  every fork, not only the one the walk took. A block whose predecessor the store
  does not hold is on no chain the client can name and is not in this list.
- **`accepted`**, **`held`** — the verdicts over exactly those blocks. `held` is
  *stored but unvalidated* ([`spec/05-processing-model.md`](../spec/05-processing-model.md),
  "Block reception"): neither accepted nor refused.
- **`rejected`** — how many blocks a source handed over that a validation rule
  showed wrong. They are not stored, so they appear in no other field.
- **`pursuits`** — one entry per source whose advertised tip the client had to
  pursue backward (`spec/07-transport.md`, "Pursuing an advertised tip"), with
  `end` being one of the three names that section settles on: `held`, `genesis`
  or `failed`.
- **`forks`** — the positions the client holds more than one block of the author
  at, ascending by the lowest digest in each; `prev` is `null` for the genesis
  position, where two genesis blocks are a fork in the strict sense of validation
  rule 9. `siblings` is ascending by digest.

The Go definition of the document is `go/internal/interop`; the TypeScript one is
`ts/scripts/sync.ts`. Both write it with two-space indentation, the keys in the
order above, and a trailing newline, so a plain `diff` is readable — but the
harness compares the parsed documents, so key order is a courtesy and not a
requirement.

## The two binaries and the two scripts

Both sides expose the same two programs with the same flags, which is what makes
the harness a table rather than a special case per implementation.

**A server** over a directory of `.block` files:

```bash
go run ./cmd/dialog-serve -chains DIR [-addr HOST:PORT] [-prefix PATH] [-announce]   # from go/
node ts/scripts/serve.ts  -chains DIR [-addr HOST:PORT] [-prefix PATH] [-announce]   # from the repository root
```

It writes **one line of JSON to stdout** before it begins serving, so that a
script can learn the port the kernel gave it:

```json
{"addr":"127.0.0.1:41751","base_url":"http://127.0.0.1:41751/dialog/v1","blocks":14,
 "chains":[{"author":"b5ua…","tip":"bafyrei…","blocks":6}]}
```

`chains` is ascending by author key, `tip` is the constructive tip and is `null`
for an author whose genesis block the directory does not hold. The default
`-addr` is `127.0.0.1:0`, which asks the kernel for a free port. `-announce` also
serves the profile's one write operation; without it the server is a read-only
mirror, which is conforming and is the default.

**A client**:

```bash
go run ./cmd/dialog-sync -source URL [-source URL …] -authors KEY[,KEY…]            # from go/
node ts/scripts/sync.ts  -source URL [-source URL …] -authors KEY[,KEY…]            # from the repository root
```

`-source` is repeatable and also accepts a comma-separated list. `-authors` is
comma-separated and its order is the order the chains are synced in, which
matters where one chain's blocks reference another's. `-from genesis` (the
default) or `-from held` chooses where a source not asked before is asked from,
as above. The summary goes to stdout and nothing else does.

Neither program stores anything on disk, and the client keeps nothing between
runs: every run starts from an empty store, so a summary is a statement about
what this exchange delivered and not about what a previous one left behind.

## The fixtures

`fixtures/` is generated, never hand-edited, under the same rule as `vectors/`
and `demo/chains/`:

```bash
cd go && go run ./cmd/geninterop          # write
cd go && go run ./cmd/geninterop -check   # assert the committed files are current
```

Regeneration is byte-identical: the author keys are seeded constants and every
block's timestamp is fixed, so a diff under `fixtures/` or `expected/` means a
digest moved and every claim quoted here and in the harness is stale. CI runs
`-check`.

The two scenarios are the two shapes of divergence the profile has to be able to
see, and in both of them **each server is honest**: every server serves a
complete chain from its genesis block to the tip it reports, skips nothing, and
answers `siblings` truthfully. Neither can be caught lying, because neither is
lying. Only a client that asks both and compares sees anything at all, which is
the multi-source rule's entire content.

## What this does not prove

- **A pursuit that fails is not crossed.** The `failed` end of the walk — a
  source that will not serve the block it advertised, bytes that hash wrong, the
  client's own bound — is covered by each implementation's own tests against its
  own misbehaving fixtures, because a server built to misbehave is not a server
  the other implementation should have to host.
- **Only the read operations are crossed.** `announce` is implemented on both
  sides and is not part of the harness yet.
- **Nothing about privacy, L2 or L3.** Those are node behaviour rather than
  interop surface, exactly as `ts/`'s scope says.
